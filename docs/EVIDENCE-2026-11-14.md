# BitOS Pay reference core — evidence 2026-11-14

Status: **Local synthetic evidence only.** This record does not claim production,
pilot, CI, real-money or live-provider verification. Blink and Strike adapter
tests use mocked HTTP responses; no funded provider account was called.

## 1. Scope

PAY-T36 adds direct Blink and Strike adapters behind the existing
`LightningProvider` port:

- `PAY_LIGHTNING_PROVIDER` accepts `mock`, `lnbits`, `blink` and `strike`.
- Blink uses `lnInvoiceCreate`, `lnInvoicePaymentStatusByHash` and
  `lnInvoiceCancel`; the live configuration requires an API key, BTC wallet ID
  and Svix `whsec_...` secret.
- Strike uses a BTC-denominated receive request and the receives API; the live
  configuration requires an API key and webhook HMAC secret.
- Blink `POST /v1/providers/blink/webhook` verifies Svix headers over the raw
  body with a five-minute timestamp window and processes `receive.lightning`.
- Strike `POST /v1/providers/strike/webhook` verifies `X-Webhook-Signature` over
  the raw body, resolves `data.entityId` to a payment hash and verifies the
  completed receive and amount.
- Both routes re-query the provider and use the existing provider-event,
  settlement, ledger and duplicate-handling path.
- Strike receive requests have no adapter cancellation; `cancelInvoice` returns
  false and live cancellation fails closed.

Not implemented: live status-polling worker, live refunds, payouts, KYB, provider
credential isolation, merchant-owned Blink/Strike balances, failover, live
reconciliation, testnet/mainnet provider run.

## 3. Limits

- Both adapters are mock-tested only. Provider API fields and behavior can
  change; no live integration, funded account or provider sandbox run exists.
- The Blink status endpoint does not restate the invoice amount; the proof binds
  the created invoice amount and payment hash rather than re-reading an amount.
- Blink intra-ledger callbacks and callbacks without a payment hash are ignored.
- Strike webhook secrets have no timestamp in the signature; replay protection
  relies on provider-event idempotency and payment-hash binding.
- Webhook loss was not recovered at this date; see the 2026-11-15 update below.
- Blink and Strike are custodial providers. A deployment is single-account and
  does not provide per-merchant fund isolation.
- No security, legal, custody, KYB or reconciliation review exists.

## 4. Update 2026-11-15: live status reconciliation

The server worker now calls `SettlementService.reconcileLiveInvoices()` on each
tick. It selects `ISSUED` invoices plus locally `EXPIRED` invoices from the last
24 hours whose intents are `livemode`, checks the live provider by the attempt's
provider reference (Blink and LNbits use the payment hash; Strike uses the
receive-request id), and calls the same `settleLive` path only when the provider
reports `SETTLED`/`PAID`. Open invoices are checked at most once per 10 seconds;
expired ones at most once per 60 seconds. A missing callback no longer leaves a
live intent pending indefinitely.

The provider proof time decides late settlement. Blink reads the receive
transaction's `createdAt` through `transactionsByPaymentHash`; a payment made
before the invoice expiry can transition `EXPIRED` to `SUCCEEDED` and post
through the normal ledger path, while a payment at or after expiry is
quarantined. The path re-verifies the provider proof, remains idempotent with
callbacks, and never polls sandbox invoices.

The Blink webhook secret is issued by Blink's Svix tenant. It is retrieved from
the **Callback Portal** linked on the Blink Dashboard **Callback Endpoints**
page; `callbackEndpointAdd` does not return it. This has not been run against a
funded Blink account, and the tests use a synthetic live provider. The worker is
single-account only and is not shared-live, failover or provider-history
reconciliation evidence.
